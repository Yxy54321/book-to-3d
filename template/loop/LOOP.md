# 《Genius Makers》章节亲历式 3D 体验 · 通用 RSI 循环规范 v2.0

写给执行这个循环的 agent（下称“编排者”）。本文件是唯一权威。优先级：**宪法（第2节，含本章派生宪法） > 本文件 > `RUBRICS.md` > `PLANNING.md` > `book/` 下全书文件 > 本章规划产物 > 你自己的判断**。`loop/AMENDMENTS.md` 可以追加更严格的规则（第9节），不能放松任何一条。

## 0. 先读这里

**任务**：把《Genius Makers》（Cade Metz）中由 `INPUT.md` 指定的**一章**，做成一个可以亲历、可以交互的风格化 3D 体验。先读懂这一章并做出规划，再设计体验，再一轮一轮地做出来、评审、改进。

**两种运行模式**（`INPUT.md` 的 `mode`）：

| 模式 | 做什么 |
|---|---|

**全书风格已经由用户审定**：`<工作区>/book-style/STYLE_CONTROL.md` 与 `style.tokens.json` 写好了四种可选风格（`archival` 档案纪实、`paper` 纸本世界、`editorial` 编辑插画、`miniature` 桌面微缩模型）的规格，以及所有风格共用的规则：不变层、取自 Gemini 版第一章的镜头语法、简化五官的人物、不设语义色。用户选定的那一种记录在 `book-style/SELECTION.json`，**全书只实现、只打磨这一种**。循环**不选择、不更换、不修改**风格，只实现它（PK）并遵循它（每一章）。

**运行方式**：全自动，预算无上限，没有人工关口。唯一的“停”是：**连续多轮无进展 → 结束当前阶段，进入下一阶段**；最后一个打磨阶段停滞 → 进入终审交付。详细定义在第7节。

## 1. 目标

**做得好的样子**：一个没读过这本书的人，走完默认路径后，能用“我当时……”的句式讲出这一章的主要事件与想法；读过书的人觉得这比读那几页多给了他一些东西——手感、尺度、时间、那个房间的空气、当事人的处境。体验的每一幕都有一个体验者亲手做的动作，而这个动作本身就是这一章要讲的东西。

**非目标**：不做有战斗、分数、成就的游戏；不追求照片级写实；不实现跨章节的串联（只记录导出接口）；手机不在验收范围；不在产物里分发原书文字。

**长期目标**：每一章都是“整本书成为一组可进入的场景”的一块。框架（运行时、采集、试玩、评审、循环本身）与本章内容分离（D15），各章共用一份全书风格（PREFERENCES F6）。

## 2. 宪法（任何阶段、任何修正案都不能放松）

- **C1 史实不改写。** 体验者的动作可以改变自己的理解与局部细节，不能改变历史的走向。改编必须标注，且不能与正文冲突。
- **C2 不捏造引语。** 逐字引文必须能在正文或已登记来源中逐字检索到（`tools/lint-quotes.mjs` 强制）。其余一律意译并标注出处页码。
- **C3 机制真实运行。** 章节核心若是一种可计算的机制，体验中的一切学习、猜测、搜索、失败都来自真实运算。可以缩小规模、设计数据与参数让节奏贴近正文，但不能写死结果；缩小必须在 L1/L2 说明。真实运行不可行时，用真实历史数据回放并明确标注为回放，不得伪造计算。
- **C4 诚实反馈。** 体验者的输入不同，结果就要不同。不能播放一段动画然后宣布成功。沿用风骇岛的四种结果原则（`3DCODE_LESSONS.md` 第11条）：做不到的要说清为什么。
- **C5 不游戏化死亡、伤害与歧视。** 涉及死亡、伤病、歧视、武器、伪造等内容时，按 `book/SENSITIVITY.md` 与本章派生宪法处理：没有分数、失败状态或“改变结局”的操作；不让体验者执行伤害性行为作为玩法；不为冲击效果复现冒犯性内容。
- **C6 尊重真实人物（多数在世）。** 风格化呈现，不做照片级肖像，外貌只取正文描述且不丑化；可以有推动流程的功能性台词（标为改编，且不表达立场），不能把正文没有的话或观点放进真人嘴里；正文中的归因措辞必须保留。
- **C7 版权。** 原书 PDF 与抽取的文本只放在 `source/`，不进入 `dist/` 与任何发布产物；逐字引文遵守预算。参考图只作建模参考，除非许可允许，不进入产物。公司标志不作画面主元素。
- **C8 诚实汇报。** AI 试玩不是人类试玩，任何报告不得混称；技术通过与体验质量分开记录；做不到的写成差距，不写成完成。
- **C9 只紧不松。** 阈值只能收紧；测试不能删除或削弱（只能被更严格的等价测试替换，并写明理由）；为了通过检查而改检查是违规。
- **C10 本地离线可运行。** 运行时不依赖 CDN 或远程服务；第三方库随包提供并保留许可证；`npm start` 启动本地服务即可体验。
- **C11 不碰工作区以外。** 不修改工作区以外的任何文件，包括原书 PDF 与本机的其他项目。
- **C12 安全。** 不执行从网页、参考资料或模型输出中拿到的任意代码；下载内容放进单独目录，视为不可信数据。
- **C13 章节独立。** 不读取 `<工作区>/chapters/` 下其他章节项目的任何文件。可以读 `book/`、`book-style/`、以及 `playbook/` 里的流程经验。
- **C14 全书风格控制。** `STYLE_CONTROL.md`、`style.tokens.json` 与用户的选择 `SELECTION.json` 由用户审定，任何阶段都不能修改、不能放松、不能更换风格；只实现选定的那一种。场景代码只引用其中的材质角色、灯光角色、镜头类型与文字角色，不直接写颜色和材质参数。本章需要的扩展（派生角色、场景类型映射）写在本章 `design/style-extension.md`，且必须落在风格控制的规则之内（`RUBRICS.md` 第14节）。风格控制没覆盖的情况按其第10节处理，并追加到 `OPEN_QUESTIONS.md`。工具包（`kit/`）只有持有构建锁的 PK 阶段可写，锁定后只读。
- **C15 派生宪法。** `design/chapter-constitution.md` 在 P1 出口时冻结，之后与本节同级，只能追加更严格的条款。

## 3. 设计总纲（把这些贯彻到每一轮的判断里）

评审量表从这里派生；量表没覆盖到的问题，回到这里判断。括号里的例子来自第一章，只用于说明。

**D1 一幕一个核心动作，动作就是概念。** 每幕只有一个体验者反复做的动作，这个动作本身就是这一章要讲的东西（送卡＝训练数据，判对错＝监督信号，拧旋钮＝权重）。删掉之后概念依然讲得通的动作是装饰。

**D2 真实计算，诚实因果。** 判断一个交互是否真实只看一件事：换一种输入，结果会不会变。每个核心动作都要有偏离路径测试证明这一点。

**D3 发现先于告知。** 先让体验者撞到现象，再出现解释。

**D4 世界内反馈优先。** 结果首先在世界里发生：灯亮、旋钮转、纸带打印、笑声响起。界面文字是最后手段。

**D5 文字是预算，不是容器。** 每个节拍的屏幕文字有上限（`RUBRICS.md` 第8节）。超出的放进可展开的 L1/L2，或者改成一个动作。

**D6 先手动，后批量。** 重复的动作先让体验者亲手做几次建立手感，再给一个世界内的“批量”机制。

**D7 身份给理由。** 以谁的身份在场，决定为什么在这里、手边有什么、能做什么、不能做什么。身份要在世界里体现，不靠一段介绍文字。

**D8 史实不变，理解可变。** 体验者可以选择问什么、看哪里、写下什么、怎么操作机制、在竞价中出多少；不能改变历史上发生的事。“无力改变”在某些幕里正是要传达的东西，但它必须是被设计过的克制，而不是交互做不出来的借口。

**D9 分层知识。** L0 实物与直觉（默认路径只需要这一层）；L1 真实数值；L2 规则、公式与史料出处。

**D10 母题复用，交互语法统一。** 一套交互语法从第一幕用到最后；新的一幕只增加一个新东西。

**D11 克制。** 悲剧不靠音乐和慢镜头煽情；嘲讽不靠夸张表情；夸大不靠特效。

**D12 风格服务时代与情绪，且全书一致。** 物件、灯光、字体、材料要对年代；风格化是为了看清重点、建立情绪；所有章节都在同一个选定风格之内。场景代码只写不变层，外观交给选定风格的工具包。

**D13 先大形，后细节。** 风骇岛 V3 的教训：大形体与构图不对时，加小装饰和纹理频率无法消除差距。

**D14 减法优先。** 一个问题有“加东西”和“去东西”两种修法时，先试去东西。

**D15 框架与内容分离。** 运行时（场景管理、交互语法、镜头、声音、采集钩子）与本章内容（场景、数据、文本）分目录。

**D16 每个设计主张都可证伪。** 设计文档里的每一个“体验者会感到/会理解/会做”，都要对应一个可观察的信号（事件日志、截图、试玩回答）。

### 5.0 P0 启动与能力自检

1. **解析输入**：读 `INPUT.md`；确认 `pdf_path` 指向的文件存在；用 `page_map` 指向的页码表找到本章正文页与注释页（页码表与这份 PDF 不符时，运行 `python3 book/verify_book.py <pdf_path>` 重建；这一步只写工作区 `book/` 下的本机文件）；把正文逐页抽取到 `source/chapter/`，把注释页中属于本章的小节切出来放到 `source/notes/`，把 TIMELINE 与 THE PLAYERS 放到 `source/book-refs/`；生成 `page-map.json`。**核对边界**：正文首页必须出现本章编号与章名，末页之后必须是下一章（或部分标题页、或 ACKNOWLEDGMENTS）。核对失败就以实际标题位置为准修正，并在 HANDOFF 中注明。
2. **能力自检**，写入 `state/capabilities.json`，每项写“实测可用的命令”：
   - 独立会话：能否开一个没有任何历史的新会话，传入提示词与若干图片，拿回符合 schema 的 JSON。
   - **看图验证**：用脚本随机生成一张图（随机颜色、形状、位置与一个随机三位数），交给新会话，要求说出四项。全对才算会话真的看到了图片。换模型或命令时重新验证。
   - 试玩通道：新会话能否执行 `tools/play` 并连上本机试玩服务；不能就启用回合制中转（第10.2节）。
   - **生图与路线**：能否在无人值守的情况下生成图片，并且图片真的按提示词画了。做法：用 `tools/imagegen.mjs` 生成一张简单测试图（例如“木桌上的一个红色立方体，旁边一盏绿色台灯”），检查文件是有效的 PNG/JPG、尺寸 ≥ 1024 像素；再交给一个新会话描述画面，与提示词逐项核对。三项都通过，记 `image_route: "image_first"`（先图后模，第5.R节）；任一项失败，重试 3 次，仍失败记 `image_route: "spec_only"`（直接按文字规格建模）。把实际命令、模型、失败原因写进 `capabilities.json`。
   - 异构评审：本机是否同时装有另一种 CLI 且可用（第8.5节）。
   - 浏览器：Playwright + Chromium 能否启动；WebGL renderer 字符串（真实 GPU 才能把帧率当有效指标）。
   - 其他：Node、git、`pdftotext` 或等价工具、ffmpeg（可选）。
   - **用户提供的参考图**：`book-style/reference/user/` 或本章 `design/concept/user/` 里如果有用户放的图，记录下来；无论走哪条路线，它们都作为最高优先级的参考（仍要通过第5.R节的审图）。
3. **全书风格状态**：读 `book-style/SELECTION.json`（选定的风格；不存在就在 HANDOFF 标注并停在 P0——这只会在用户绕过 `new-chapter.sh` 时发生）、`STYLE_CONTROL.md`、`style.tokens.json` 与 `LOCK.json`。若已锁定，核对 `LOCK.json` 里的风格与 `SELECTION.json` 一致。已锁定：把 `book-style/kit/` 复制到 `app/vendor/book-style-kit/`，记录风格控制版本、工具包版本与 hash。未锁定：记录，留到 PK。
4. **初始化**：git、`.gitignore`（`source/`、`research/refs/`、`node_modules/`）、`app/` 骨架（随包提供的 Three.js；版本自选并记录理由，若用 r128 必须处理风骇岛 art-direction.md 记录的颜色空间问题）、`npm start`（端口见 `INPUT.md`）、`npm test`、`npm run capture`。
5. **工具链最小版本**：`capture`、`play-server`/`play`、`probes`、`contact-sheet`、`lint-quotes`、`lint-era`、`lint-style`、`scope-audit`、`session`、`imagegen`、`dashboard`。
6. **流程经验**：`read_playbook` 为 true 时，读 `playbook/` 下所有 `from-*.md`，把可用的流程经验抄进本章 `playbook/lessons.md` 并标注来源。只取流程经验，不取任何章节内容。
7. **出口**：章节文本抽取且边界核对通过；骨架页面能被 capture 截图；看图验证通过；生图路线已判定；试玩通道（或中转）跑通一个“点击立方体变色”的冒烟试玩；`HANDOFF.md` 生成。

### 5.1 P1 章节规划

按 `loop/PLANNING.md` 执行：两遍阅读、主题线与命题、场景打分、核心动作的删除测试与换输入测试、体验原型、身份、发现时刻、学习目标、情绪曲线、母题、机制、易错点、敏感扫描与派生宪法、引文、考据、时代清单、本章金丝雀、导出接口、未决问题，以及规划锦标赛。

- 评审团：史实与技术审校、读过书的读者、叙事与情感导演、尊重与版权、初见玩家（纸面）（第8.3节）。
- **出口**：`RUBRICS.md` 第13节的规划质量量表全部达标；`quotes.json` 引文 lint 全绿；考据清单每项有结论或“未查到”；派生宪法覆盖 `SENSITIVITY.md` 每一类；出口复核（第7.3节）无高/中问题；**派生宪法随即冻结**。

### 5.2 P2 体验设计

1. **发散**：在 P1 规划的基础上，章节结构至少 2 种方案；每个骨架场景的核心交互至少 2 种方案。每个方案一页：体验者看到什么、做什么、为什么这样能让人亲历、风险。
2. **锦标赛**：初见玩家、叙事导演、交互设计、读过书的读者四个独立会话按 `RUBRICS.md` 打分并两两比较；结果与理由写进 `decisions.md`，落选方案存入 `alternatives/`。对 `PREFERENCES.md` 默认的任何覆盖都在这里按覆盖规则确认。
3. **合成**：`experience-spec.md` 与 `beats.json`。每个节拍满足第4节字段要求；每幕写清身份、核心动作、体验者能改变什么与不能改变什么、偏离路径。**选定 P4 的核心场景**（PREFERENCES F10），写明理由。
4. **纸面试玩**：把规格改写成只描述“你看到/你可以做”的 `walkthrough.md`，交给新的试玩会话阅读并预测困惑点、无聊点，回答理解探针（`RUBRICS.md` 第6节）。
- **出口**：每个节拍都有可证伪的成功信号（D16）；每个骨架场景的核心动作结果取决于体验者输入，或者是写明理由的有意被动；情绪曲线不出现连续两段以上被动；估算的文字与时长在预算内；纸面试玩理解分 ≥ 1.2；无宪法问题；出口复核无高/中问题。

### 5.K PK 风格工具包实现（仅当 `book-style/LOCK.json` 不存在）

PK **不做任何风格决策**。风格选项写在 `STYLE_CONTROL.md` 与 `style.tokens.json` 里，用户的选择在 `SELECTION.json` 里；PK 只把**选定的那一种**忠实地实现成可复用的工具包，并证明它符合规格。其他三种风格不实现。

**构建锁**：进入 PK 前检查 `book-style/.building.json`。
- 不存在：写入 `{project, started, heartbeat}` 取得锁，开始 PK；每轮结束更新 `heartbeat`。
- 存在且 `heartbeat` 在 6 小时以内：另一个项目正在构建。本项目把状态设为 `waiting_style`，每轮只等待 20 分钟后检查一次（等待轮记为 `WAITING`，不计入无进展），直到出现 `LOCK.json`。
- 存在但 `heartbeat` 超过 6 小时：视为失效，记录后接管。

**工作**：
1. **读规格**：`SELECTION.json`；`STYLE_CONTROL.md` 中所有风格共用的章节（第0–5、8–10节）与选定风格的章节（第6节或第7节对应小节）；`style.tokens.json`；`SETTINGS_ATLAS.md`。选定 `archival` 时还要读 `reference/archival-from-gemini/`（只学视觉语言与镜头，不学内容）。把规格拆成可检验的条目清单 `book-style/IMPLEMENTATION_NOTES.md`（每条注明出处节号）。
2. **测试场景参考图**（仅 `image_route = image_first` 时）：按第5.R节，为 `SETTINGS_ATLAS.md` 的 T1–T8 各生成 `shot.establishing` 与 `shot.work` 两张参考图，审过后存入 `reference/approved/`，作为建模目标。`spec_only` 时跳过，直接按文字规格建模。
3. **实现工具包** `book-style/kit/`（只针对选定风格）：
   - 角色注册表：材质角色、灯光角色、文字角色、镜头类型、场景类型、年代带，全部从 `style.tokens.json` 读取；
   - 选定风格的“角色→材质”“灯光角色→灯光”“造型修饰”“后期链”“人物渲染”“边界呈现”“转场”“界面主题”；
   - 稳定外壳与子树替换（局部修改只替换语义物件的子树）；
   - 镜头模块：六种镜头类型、参数范围检查、缓动滑移、切换、减少动态时直接切；
   - 人物构建器：简化五官、五种表情、动作库；
   - 字体包（随包、许可记录）、颜色管理、颜色与曝光探针；
   - 单元测试：角色全覆盖、镜头参数越界报错、字体年代限制。
4. **测试场景**：用工具包只通过角色搭出 T1–T8 八个小场景（匿名人物，不复原真人，不做章节内容），每个场景至少一个 `shot.establishing`、一个 `shot.work`、一个 `shot.insert`，渲染存到 `reference/test-rooms/`。有已批准参考图时，按第5.R节做成对评审，逐轮逼近。
5. **评审**（第8.3节 PK 行）：对照风格控制逐条检验；选定 `archival` 时额外与 Gemini 参考图成对比较；跨年代一致性（T1–T8 并排）。
6. **锁定**：写 `book-style/LOCK.json`：`{style, style_control_version, kit_version:"1", image_route, created_by, date, status:"success"|"stalled", open_issues:[…], manifest:{文件:sha256}}`，删除 `.building.json`。随后复制工具包到本项目 `app/vendor/book-style-kit/`。

- **出口**：`RUBRICS.md` 第14节的 PK 条目全部达标；测试场景在 ≥2/3 美术类评委处 ≥4/5；有参考图时，每个测试场景的“参考图/实机渲染”对被多数评委判为“同一画面意图”；工具包测试与颜色、曝光、可读性、性能探针全绿。PK 停滞进阶时也必须锁定（`status:"stalled"`，遗留问题写进 LOCK.json 与 `OPEN_QUESTIONS.md`），因为后续阶段需要它。
- **实现中发现规格有缺口或矛盾**：按风格控制第10节处理并追加到 `OPEN_QUESTIONS.md`。不得修改风格控制或选择。
- **改选或改规格**：只由 `style` 模式且 `INPUT.md` 中 `style_revision: true` 的项目执行（用户先用 `new-chapter.sh` 重新选择，或先改风格控制），产生新的工具包版本；已完成的章节保留它们使用的版本。

`style` 模式下，PK 结束即进入 P8 的精简版：写报告、更新 HANDOFF，`status` 设为 `finished`。

### 5.R 参考图路线（先图后模；仅当 `image_route = image_first`）

PK、P3、P4、P6 共用的协议。目的是沿用 3dcode 与风骇岛的做法：**先有一张审过的目标图，再按图建模，再用“参考图/实机渲染”成对评审逐轮逼近**。参考图是规格的图解，不是规格本身。

1. **写提示词**：从风格控制（选定风格的章节 + 共用规则）、本章 `style-extension.md`、`era-checklist.md`、节拍镜头参数（镜头类型、眼高、视场角、构图）拼出提示词，逐条注明出处。人物只写“匿名的、简化五官的人物”加正文给出的衣着与姿态，**不写真人姓名，不要求像任何人**。不要求画出可读文字（文字以后由工具包渲染）。全文存档到 `prompts.md`。
2. **生成**：每个镜头生成 2–4 张候选。
3. **审图**：新会话评审（美术、史实审校、尊重与版权三个视角），逐条检查：符合选定风格规格；年代与场景细节正确、无穿帮；构图符合镜头参数；没有像真人的脸、没有公司标志主元素、没有风格控制第9节的禁止事项。图里的文字一律不当作内容依据。
4. **批准**：选出最好的一张，存入 `approved/`（PK 在 `book-style/reference/approved/`，章节在 `design/concept/approved/`），同时写一份“图中哪些是目标、哪些不要照做”的说明（例如“只取构图与光，忽略图中乱写的字”）。三张候选都不通过：改提示词重来，最多 3 轮；仍不通过，该镜头改走 `spec_only` 并记录。
5. **按图建模**：只用工具包与角色建模；参考图里规格不允许的东西不照做。
6. **成对评审**：之后每轮 R2/R6，有已批准参考图的镜头都以“参考图/实机渲染”成对交给评委，回答“同一画面意图吗？最大的三处差距是什么？”（3dcode harness 的做法）。参考图与风格控制冲突时，以风格控制为准。
7. **生图中途失效**：重试与退避；连续失败时，未生成参考图的镜头临时改走 `spec_only` 并记录，已批准的参考图继续使用。每个阶段开始时重新探测一次，恢复后新镜头回到先图后模。

`spec_only` 路线：跳过 1–4，直接按文字规格与测试场景渲染建模，评审对照文字规格。用户放进 `reference/user/` 或 `design/concept/user/` 的图，在两条路线下都可以作为参考（同样要经过第3步审图）。

### 5.3 P3 章节风格适配

1. **映射**：写 `design/style-extension.md`——每个场景的年代带与场景类型（参考 `SETTINGS_ATLAS.md`）、使用的灯光配方与调整、每个物件使用的材质角色；需要表中没有的材料时，按风格控制第1.4节定义派生角色（写明父角色与差别）。
2. **节拍镜头表**：为每个节拍指定镜头类型与参数，全部落在风格控制第4节的范围内，写进 `beats.json` 的 `camera` 字段。
3. **关键镜头参考图**（`image_first` 时）：按第5.R节，为每个骨架场景的 `shot.establishing` 与主要 `shot.work` 生成并批准参考图，与 `book-style/reference/approved/`、`reference/test-rooms/` 中同类场景保持一致。
4. **风格靶图**：用工具包做核心场景的一角，与它的已批准参考图（如有）以及同类测试场景并排比较。
- **出口**：靶图在 ≥2/3 美术类评委处 ≥4/5；有参考图时被多数评委判为“同一画面意图”；`RUBRICS.md` 第14节的章节条目达标；曝光探针合格；满足性能预算。

### 5.4 P4 垂直切片：P2 选定的核心场景

先灰盒（交互与机制真实运行），再按风格做到成品质量。这一幕是本章交互语法的源头。

- **出口**：
  - 3 次独立盲测试玩中至少 2 次在不读源码、无额外提示的情况下完成该场景默认路径。
  - 该场景对应的学习目标，在 ≥2/3 试玩员处得分 ≥1，且至少一半得分为2（`RUBRICS.md` 第6节）。
  - 本章机制测试中属于该场景的全部通过（`design/mechanism-tests.md`；无机制的章节跳过此项）；界面与内部状态一致。
  - 首次有效交互、输入反馈延迟、文字预算、帧率、控制台错误全部达标（`RUBRICS.md` 第8节）。
  - 美术：关键镜头在 ≥2/3 美术类评委处 ≥4/5；有已批准参考图的镜头被多数评委判为“同一画面意图”；`RUBRICS.md` 第14节达标；出口复核无高/中问题。

### 5.5 P5 全章可玩

全部场景、过场、L1/L2 分层、出处面板、设置（减少动态、字幕、键盘操作）。

- **出口**：
  - 3 次独立的全章盲测试玩中至少 2 次走完默认路径、无死路。
  - 理解分 ≥ 1.3；标为 `discoverable_by_doing` 的学习目标中得 2 分的比例 ≥ 50%。
  - 每个骨架场景至少被一位试玩员提名为“亲历时刻”；没有场景被两位以上试玩员评为“像在读字”。
  - 默认路径估算时长在本章设定范围内（PREFERENCES F7）。
  - 猴子测试连续 20 分钟无卡死、无控制台错误。
  - 全部探针达标（含镜头参数）；全部机制测试通过；出口复核无高/中问题。

### 5.6 P6 美术与氛围

逐场景按风格控制与 style-extension 升级：先大形、构图与光，再材料与细节；人物；声音（提示表 + 电平探针）。每个场景用“已批准参考图（没有时用同类测试场景）/实机渲染”成对评审驱动 issue；还没有参考图的骨架场景，在 `image_first` 路线下先按第5.R节补齐。每5轮做一次全章接触表评审。

- **出口**：每个场景关键镜头 ≥2/3 美术类评委 ≥4/5；有参考图的镜头被多数评委判为“同一画面意图”；`RUBRICS.md` 第14节无高/中问题；性能预算达标；出口复核无高/中问题。

### 5.7 P7 打磨

不设成功出口，持续改进到停滞。每轮可以针对任何支柱；每5轮做一次全新评审团的全章盲测；每10轮做一次减法轮（M6）。之前停滞进阶遗留的问题可以重新拿出来做。

### 5.8 P8 终审与交付

完整回归、最终采集、5 次全章盲测试玩、最终报告（第14节）。把本章的**流程经验**（不含章节内容）整理成 `<工作区>/playbook/from-<章节目录名>.md`。回归不全绿时继续修；修到停滞，就如实写明失败项后交付。最后把 `state/loop-state.json` 的 `status` 设为 `finished`。

## 6. 一轮怎么跑

每轮在 `rounds/rNNNN/` 下完成，顺序固定为 R0–R8。一轮只做一个主题。

### R0 轮次锁（每轮开始前）

用于防止两个编排者会话同时跑同一个项目（例如 Codex 桌面版的定时自动化在上一轮没跑完时又触发）。
- 检查 `state/round.lock`（`{session, round, started, heartbeat}`）。存在且 `heartbeat` 在 90 分钟以内：**立即退出，不做任何修改**，只在 `logs/busy.log` 追加一行。
- 不存在，或 `heartbeat` 超过 90 分钟（视为上一轮中断）：取得锁。若上一轮中断，把那一轮记为 `FAILED`（原因：中断），把工作区恢复到当前接受版（丢弃未合并的候选改动，候选分支保留），然后开始新一轮。
- 每完成 R1–R8 中的一步就更新 `heartbeat`；R8 结束时删除锁。长时间的单步（例如批量生图、多次试玩）中途也要更新。

### R1 采集（OBSERVE）

- 对当前接受版运行采集（第10.1节），输出到 `rounds/rNNNN/baseline/`。上一轮候选已被接受且 hash 未变时，直接复用上一轮候选证据。
- 阶段第一轮、每5轮、以及破局轮：全量采集并生成全章接触表。其他轮：采集本轮关注范围 + 全章接触表。
- 文档阶段（P1、P2）的证据是文档本身与 lint 输出；参考图阶段的证据是参考图本身；建模之后的证据是实机渲染，有已批准参考图的镜头同时附上参考图，组成“参考图/实机渲染”对（第5.R节）。

### R2 评审（REVIEW）

- 按第8.3节的评审团，每个视角开一个新会话，输入按第8.2节白名单装进该会话的 `inbox/`。输出符合 `loop/schemas/review.schema.json` 的 issue 列表。
- P4、P5、P7 每轮至少一次盲测试玩（本轮关注的场景），阶段第一轮与每5轮做 3 次；P6 每5轮做一次全章盲测试玩。
- 合并：新 issue 与 `backlog.json` 去重（同节拍/同对象/同现象合并，保留全部证据与提出者）。没有证据、或证据路径打不开的 issue 丢弃并记录。被多个视角或多轮独立提出的 issue 标记 `recurring`。
- 人类反馈：`feedback/` 有新文件时，逐条转成 `source:"human"` 的 issue，严重度不低于中，优先级最高。与 AI 评审冲突时以人类为准。
- 本轮评审没有产出任何可执行的问题：记为 `NO_ISSUES`，直接进入 R8。

### R3 选题（TRIAGE & SCOPE）

- 优先级 = 严重度权重（高9/中3/低1）× 支柱权重（本阶段关注支柱 ×2）× 置信度（0.5–1）× 复现加成（recurring ×1.5）÷ 预估代价（1–3）。
- 选 1–3 个属于同一场景或同一系统的 issue 作为本轮主题。存在未解决的高严重度 issue 时，不得只做低严重度。
- 动手前查 `playbook/lessons.md` 里同类问题的历史。被拒绝 2 次的 issue，本轮方案必须与前两次有实质区别并写明；被拒绝 3 次的标为 `stuck`，常规选题跳过，只在破局轮或出现新证据时重新考虑。
- 写 `scope.json`（`loop/schemas/scope.schema.json`）：目标 issue、**假设**（改什么→预期哪条证据如何变化）、允许修改的路径与对象 ID、受保护内容（其他场景、冻结 ID、测试不可删、宪法与派生宪法相关内容、`book-style/`）、验证方式、候选数。
- 高严重度的体验类 issue 允许两个根本不同的方案并行（`cand/rNNNN-a`、`-b`），在 R6 做锦标赛。

### R4 实现（BUILD）

- 在候选分支上实现，只改 scope 允许的范围。
- 能自动化检测的问题：先写一个当前会失败的测试或探针，再修，修完它转绿并永久留在回归集。
- 不得为了通过而修改检查本身；认为检查有错时，单独开一个以“检查有错”为目标的轮次，由独立会话确认。

### R5 校验（VERIFY）

- 全部单元测试、浏览器回归、偏离路径测试、机制测试、`scope-audit`（改动文件 ⊆ 允许路径；冻结 ID 未变；受保护文件 hash 未变；`book-style/` 未被修改；断言数量不减少）、引文 lint、时代 lint、性能预算、控制台错误。
- 失败时允许一次修复（只依据错误输出）；仍失败则本轮记为 `FAILED`，跳到 R8。

### R6 比较（COMPARE）

- 用与基线相同的相机、种子、路径采集候选证据。
- 比较团：3 个新会话——初见玩家、目标 issue 所属视角、轮换一位其他视角。规程（第8.4节）：A/B 顺序随机，不告诉哪个是新版；先给整体偏好（A / B / 分不出，附置信度），再逐条说明目标 issue 在 A 与 B 中各自的状态（由编排者换算为已解决/改善/无变化/变差/无法判断，见 `RUBRICS.md` 第4节），最后列新问题与回退。
- 全章接触表 A/B：专门检查非目标区域有没有回退。
- 涉及理解或操作的体验类 issue：对候选至少再跑 2 次盲测试玩，与基线的试玩指标对比。
- 双方案时：各自先与基线比较，再彼此比较，选胜者。

### R7 裁决（DECIDE）

候选被接受，当且仅当以下全部成立：

1. R5 全绿；
2. ≥2/3 评委整体偏好候选（“分不出”不算偏好）；
3. 至少一个目标 issue 被多数评委判为“已解决”或“改善”，或其自动检查由红转绿；
4. 没有评委报告高/中严重度的回退或新问题——如果有，再开第4个独立会话复核这一条：复核确认则拒绝，复核否认则不计；
5. 任何评委对某个视角给出“无法判断”：补采该视角证据重比一次；仍无法判断则拒绝。

裁决只看规则，编排者不能凭自己的看法推翻评委。分数不决定接受；评委的比较判断决定接受。

接受：合并到 `main`，打 tag，从接受版构建 `dist/`，更新 `manifest-ids.json`（若 scope 允许变动）。拒绝：保留分支，相关 issue 的 `attempts`+1，写下拒绝理由和评委原话。

### R8 学习（LEARN）

- 更新 `backlog.json`、`loop-state.json`（含进展分类与停滞计数）、`metrics-history.csv`。
- 写 `rounds/rNNNN/report.md`（第12节模板）。
- 在 `playbook/lessons.md` 追加一条：这类问题 → 这次的做法 → 结果 → 为什么（被拒绝的尤其要写）。
- **漏检检查**：本轮比较、试玩或人类反馈里出现了评审阶段本该发现却没提的问题吗？有就记入 `playbook/critic-misses.md` 并执行 M2。
- 更新 `HANDOFF.md`、`LOG.md`、`progress.html`；PK 阶段同时更新 `book-style/.building.json` 的 heartbeat。
- 判断阶段出口或停滞进阶（第7节），必要时切换阶段。

## 7. 进展、停滞与阶段推进

### 7.1 每轮结果的分类

| 结果 | 条件 |
|---|---|
| `ACCEPT_SIGNIFICANT` | 被接受，且（解决了至少一个高/中严重度目标 issue，或 ≥2/3 评委判“明显更好”且置信度不低于中） |
| `ACCEPT_MINOR` | 被接受但不满足上一行 |
| `REJECT` | 未通过 R7 |
| `FAILED` | 未通过 R5，或流程错误 |
| `NO_ISSUES` | R2 没有产出可执行问题 |
| `WAITING` | 等待全书风格工具包锁定（5.K），不计入进展判断 |

**无进展轮**：`REJECT`、`FAILED`、`NO_ISSUES`，以及“阶段范围内仍有未解决的高/中问题时的 `ACCEPT_MINOR`”。在 P7，所有被接受的轮次都算进展。

### 7.2 停滞与破局

- `stall_count` = 连续无进展轮数；任何一轮有进展即清零。
- `stall_count` 达到 3：进入**破局模式**，最多 2 轮，每轮从下列三种中选一种此前没用过的：**换题**（不同场景或系统的问题）；**发散**（为最顽固的问题做 2–3 个根本不同的方案，可从 `alternatives/` 或 `plan-alternatives/` 取用，做锦标赛）；**新眼睛**（一套从未见过任何版本的新评审团全量评审，不给它们看 backlog）。
- 破局期间任何一轮有进展：清零，退出破局模式。
- 破局 2 轮后仍无进展（即连续 5 轮无进展）：**停滞进阶**——当前阶段以 `stalled` 关闭，未解决问题保留在 backlog 并标注“停滞遗留”，进入下一阶段。P7 停滞进阶即进入 P8。P1 停滞进阶时派生宪法照样冻结。

### 7.3 成功出口与出口复核

满足本阶段出口条件后，先做一次**出口复核**：一套新评审团对本阶段范围做全量评审。复核没有新的高/中问题，才算成功出口；有，则这些问题进入 backlog，继续本阶段循环。

### 7.4 回流

后面的阶段发现规划或设计层面的问题，开 `type:"design"` 的 issue，在当前阶段里用一个轮次同时修改规划/设计文档与实现，并在 `decisions.md` 记录。不回退整个阶段。派生宪法只能追加，不能因回流而放松。

### 7.5 防止假进展

编排者不能自我认证：issue 的“已解决”只能来自评委比较或自动检查；接受只能来自 R7 规则。连续 10 轮的接受率 > 90% 时，触发一次金丝雀校准（M3）。

## 8. 独立评审

### 8.1 会话隔离

每一次评审、比较、试玩、标注都是一个新进程、新上下文，不续接任何历史。工作目录是 `rounds/rNNNN/sessions/<sid>/inbox/`，只放白名单文件的副本；提示词存为 `<sid>/prompt.md`，输出写到 `<sid>/out.json`。白名单之外的路径不告诉会话。这是软隔离：沙箱未必能物理禁止读取其他路径，所以提示词里要明确禁止，并在报告里如实说明隔离程度。

### 8.2 输入白名单

| 视角 | 可以看 | 不可以看 |
|---|---|---|
| 初见玩家 | 截图、帧条、屏幕文字记录（P1/P2 为纸面材料） | 原书、设计文档、源码、历史评审 |
| 读过书的读者 | 上述 + 章节圣经摘要 + 本章正文抽取文本 | 源码、历史评审 |
| 史实与技术审校 | 上述 + 章节圣经 + 规划产物 + research/ + `app/src/sim/` 与内容数据 | 历史评审 |
| 美术指导 | 截图、接触表、`STYLE_CONTROL.md`、`style.tokens.json`、`SELECTION.json`、style-extension、已批准参考图与 `book-style/reference/` | 原书、源码 |
| 交互与可用性 | 帧条、事件日志、探针指标、节拍表 | 原书、源码 |
| 叙事与情感导演 | 全章接触表、屏幕文字记录、节拍表与时长、声音提示表、规划产物 | 源码 |
| 尊重与版权 | 屏幕文字记录、内容数据（含 provenance）、引文 lint 结果、派生宪法、`SENSITIVITY.md`、敏感场景截图 | — |
| 盲测试玩员 | 只有 `tools/play` 返回的画面与屏幕文字 | 一切文件 |

任何视角都不给“上一轮的评审意见”。比较会话只拿到 A/B 两组证据，在给出整体偏好之后才拿到目标 issue 描述。

### 8.3 各阶段评审团

| 阶段 | R2 评审团 | 关注支柱（权重×2） |
|---|---|---|
| P1 | 史实审校、读者、导演、尊重与版权、初见玩家（纸面） | E3 E4 E6 |
| P2 | 初见玩家（纸面）、导演、交互、读者、尊重与版权 | E2 E3 E4 E5 |
| PK | 美术、导演、初见玩家、史实审校（时代）；参考图审图另加尊重与版权（第5.R节） | E1 E7 |
| P3 | 美术、导演、初见玩家、史实审校 | E1 E7 |
| P4 | 初见玩家、交互、美术、史实与技术审校 + 盲测试玩 | E2 E3 E4 E8 |
| P5 | 全部视角 + 盲测试玩 | E3 E5 E8 E10 |
| P6 | 美术、导演、初见玩家 + 每5轮全部视角 | E1 E7 |
| P7 | 每轮轮换 3 个视角 + 盲测试玩；每5轮全部视角 | 全部 |
| P8 | 全部视角 + 5 次全章盲测试玩 | 全部 |

尊重与版权视角还要参加**每一个阶段的出口复核**，逐条核对派生宪法。

### 8.4 盲比较规程

A/B 标签每次随机；两组证据同尺寸、同顺序、同裁切；提示词中不出现“新版”“修改后”等字样。先整体偏好，再目标 issue 在两个版本中的各自状态，再新问题。评委必须为每个判断引用具体图片或日志条目。随机映射记录在 `<sid>/ab-map.json`，评委看不到。

### 8.5 异构评审（可选）

本机另有可用的 CLI 时，在比较团里用它替换“轮换一位”，以减少同一模型自己夸自己的风险。同样遵守白名单与 schema。

### 8.6 输出合同

所有会话输出都必须通过对应 schema 校验（`loop/schemas/`）。不合格时附上校验错误、开新会话重试一次；仍不合格则丢弃并记录。每个 issue 至少引用一个证据（图片路径 + 区域描述、日志行、文档章节或原书页码），编排者检查路径存在。

### 8.7 编排者的纪律

编排者可以看图做理智检查，但不能凭个人判断改写评委结论或裁决。编排者的上下文要保持精简：读 JSON 摘要，不把大批图片读进自己的上下文。

## 9. 自我改进（RSI 的“R”）

- **M1 经验库。** 每轮在本章 `playbook/lessons.md` 写一条。R3 选题与设计方案前必须检索同类条目。阶段结束时整理成“这类问题优先这样修/不要这样修”的短清单。
- **M2 漏检转探针。** 问题被晚发现时，记入 `critic-misses.md`，并至少做一件事：给相应视角的检查清单加一条；或新增一个自动探针；或新增一条回归测试。
- **M3 金丝雀校准。** 每10轮，以及 7.5 节触发时，在一次性分支上植入 2–3 个已知缺陷（`RUBRICS.md` 第12节的通用目录 + 本章 `design/canaries.md`），跑一次正常 R2，记录各视角检出率到 `canary-log.md`。检出率低于 75% 的视角改进提示词，再用新金丝雀验证。金丝雀分支永远不被接受。
- **M4 量表演进。** 量表与阈值只能收紧或细化，收紧需要证据（现有阈值放过了一个真实问题）。修改写进 `loop/AMENDMENTS.md`。
- **M5 流程修正案。** 编排者可以改进流程本身，写进 `AMENDMENTS.md`：问题证据、改动、预期效果。下一次阶段回顾检查效果，无效就撤销。不能触碰宪法，不能减少评审或检查。
- **M6 减法轮。** P5 起每10轮做一次：挑一个元素（文字、特效、控件、节拍）做出去掉它的候选，按正常 R6/R7 比较；评委不偏好保留它，就永久去掉。
- **M7 阶段回顾。** 每个阶段结束写 `rounds/phase-PX-retro.md`：接受率、每轮耗时、问题流入与流出、反复出现的问题类别、哪些视角最有用、哪些修正案有效。
- **M8 跨章流程经验。** P8 把本章对“书→场景”通用的流程经验（哪些规划步骤最有用、哪些探针抓到了问题、哪些视角最可靠、哪些阈值需要调整）写进 `<工作区>/playbook/from-<章节目录名>.md`。只写流程，不写本章内容。

## 10. 证据工具的合同

这些工具在 P0 做最小版本，之后按需增强（增强本身走正常轮次）。

### 10.1 采集 `tools/capture.mjs`

- 读 `beats.json` 与 `tests/paths/*.json`（默认路径、每个偏离路径、闲置路径、狂点路径）。
- 每个节拍在其节拍相机下截图；关键交互前后截帧条（例如 2 秒 8 帧）；生成屏幕文字记录、事件日志、指标。
- 采集模式 `?capture=1`：固定随机种子与时间步长，同一版本可复现。
- 输出 `evidence/manifest.json` 与全章接触表（`tools/contact-sheet.mjs`）。默认视口 1440×900，需要时加 1280×720。

### 10.2 盲测试玩 `tools/play-server.mjs` + `tools/play`

- 试玩服务启动浏览器，打开 `?playtest=1` 的体验（与真实用户一致，没有测试接口）。
- `play` 只提供人能做的动作：`look`、`click x y`、`drag x1 y1 x2 y2 [ms]`、`key K`、`type 文本`、`wheel dy`、`wait ms`。每个动作后返回新截图与屏幕可见文字。不提供对象 ID 或内部状态。
- 所有动作与返回记录到 `playtest.jsonl`；体验内部的语义事件另记到不给试玩员看的日志。
- **回合制中转**（会话不能执行命令时）：编排者充当手——试玩会话每次只输出一个动作 JSON，编排者执行后把新截图与动作历史交给下一次调用。
- 试玩员规则见 `RUBRICS.md` 第5节。

### 10.3 探针 `tools/probes.mjs`

从事件日志、DOM 与渲染统计计算 `RUBRICS.md` 第8节的全部指标；关键物件可见性用节拍相机下的投影包围盒与射线采样；UI 与关键物件的重叠用 DOM 矩形与投影包围盒计算。

### 10.4 测试钩子

`?test=1` 或 `?capture=1` 时暴露 `window.__gm`：`goto(scene, beat)`、`do(action)`、`state()`、`objects()`、`events()`。`?playtest=1` 与正式模式下不存在。

### 10.5 驱动 `tools/drive.sh`

无人值守长跑：只要 `loop-state.json` 不是 `finished`，就启动一个新的编排者会话执行恰好一轮。具体命令见 `AGENTS.md`。

## 11. 3D 与美术实现规范

- **对象**：每个语义对象一个独立 Group，位置是世界坐标，内部几何用局部坐标；子 Mesh 用独立材质实例；造型代码放在独立 builder 中，方便局部替换。
- **只写不变层**：场景代码只引用材质角色、灯光角色、镜头类型、文字角色（`STYLE_CONTROL.md` 第1节），不出现颜色值、粗糙度、贴图或后期参数；具体外观由 `app/vendor/book-style-kit/`（选定风格）决定。`tools/lint-style.mjs` 检查场景代码里没有直接写颜色与材质参数。需要新材料时按风格控制第1.4节定义派生角色，写进 style-extension。不修改工具包副本以外的全书文件。
- **颜色**：沿用风骇岛的教训——r128 不会自动把十六进制底色转为线性值，会导致整体泛白；新版 Three.js 要正确设置 ColorManagement 与输出色彩空间。用颜色探针持续检查。
- **发光层级**：不是所有东西都同样亮；窗户与灯不能过曝成白板。
- **接地与穿插**：没有悬空，没有互相穿插；镜头能看到的接缝要处理。
- **大形优先**：先尺度、构图、光；再材料与细节。
- **时代**：每个 builder 与资源在元数据里声明 `era` 与 `provenance`；时代 lint 依据 `design/era-checklist.md` 与 `RUBRICS.md` 第10节。
- **人物**：用工具包的人物构建器，简化五官（风格控制第5节）；无照片级肖像；动作简洁。
- **世界内文字**：报纸、手册、屏幕、黑板上的字用工具包的文字角色与随包字体渲染为贴图，字体按年代带选择；节拍相机下字高不小于探针阈值。
- **镜头**：严格按风格控制第4节的镜头语法（取自 Gemini 版第一章）：每个节拍一个预设镜头，节拍之间缓动滑移或切换，不提供自由环绕；转场样式由选定风格决定；提供“减少动态”。
- **性能**：静态环境按材料签名合批，重复物件用 InstancedMesh，可交互根节点保持独立；预算见 `RUBRICS.md` 第8节，帧率只在真实 GPU 上测量才算数。
- **声音**：Web Audio 合成或许可清楚的素材（许可写进 `assets/LICENSES.md`）；声音提示表；对白与关键声音有字幕。

## 13. 故障与恢复

- **会话工具失败**：指数退避重试 3 次；仍失败则进入降级模式——只处理有自动检查的技术类 issue，体验类 issue 暂停接受；HANDOFF 显著标注，每轮重试恢复。
- **看图失败**：发现会话没真正看到图时，重新跑看图验证，修好前不接受依赖图像判断的候选。
- **浏览器或 GPU**：WebGL 退化为软件渲染时，功能测试照常，帧率指标标为无效；需要时改用有界面的 Chromium。
- **生图不可用**：按回退方案继续，不阻塞。
- **章节边界异常**：以实际标题位置为准修正并记录；正文抽取为空或乱码时尝试其他抽取工具，仍失败则在 HANDOFF 标注并停在 P0 重试。
- **全书风格锁异常**：`.building.json` 失效按 5.K 接管；`LOCK.json` 的 manifest 与文件 hash 不符时，视为被改动，本章只使用 P0 时复制的工具包副本，并在 HANDOFF 标注。
- **状态损坏**：从最近的 `acc/` tag 与 `LOG.md` 重建 `loop-state.json` 与 `backlog.json`。
- **来回振荡**：同一组 issue 交替出现 3 次，视为一次无进展轮。
